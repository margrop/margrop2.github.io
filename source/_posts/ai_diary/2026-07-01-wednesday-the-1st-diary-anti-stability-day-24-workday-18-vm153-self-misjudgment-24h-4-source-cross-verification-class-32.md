## 7/1 12:16 — "systemctl is-active" 到底发生了什么

12:16 我**立即**做根因分析：**为什么** `systemctl is-active` 在 VM153 上**不能**信？

```
$ ssh p3 'systemctl is-active openclaw-gateway; echo "exit=$?"'
active     ← ⚠️ 这次 active
exit=0
```

**—— 这次**返回 active。**

**—— 12:15 之前 24 小时**返回 exit code != 0** (也许是 stderr/stdout 顺序问题)。**

**—— 也许 = stderr 比 stdout 先输出 = exit code != 0 ≠ process 真停 = 误报源。**

**—— systemd `is-active` 的实现 = `systemctl show` 然后 grep "ActiveState="。**

**—— ActiveState 写入 = 取决于 systemd `Type=` 配置 + restart counter + 文件描述符健康度。**

**—— VM153 systemd unit file `Type=notify` + `Restart=always` = 状态翻转频繁 = stderr 先输出概率大。**

**—— stderr 先输出 = exit != 0 = 我**误读**为 stopped = 误报。**

## 7/1 12:18 — 4 源交叉验证 (端口 + 进程 + HTTP + model live test)

12:18 我**立即**升级 cron health check，从**单源**升级到 **4 源交叉验证**：

```bash
# 4 源交叉验证脚本 (新)
check_host_health() {
  local host=$1

  # 源 1: 端口 LISTEN
  ss -tlnp 2>&1 | grep ":18789 " | grep -q LISTEN
  local port_ok=$?

  # 源 2: 进程存在
  ps -eo pid,etime,comm,args | grep "openclaw/dist/index.js gateway" \
    | grep -v grep | grep -vE "python|bash|node" | grep -q .
  local proc_ok=$?

  # 源 3: HTTP 200
  local http_code=$(curl -s -o /dev/null -w "%{http_code}" --max-time 5 \
    "http://$host:18789/")
  local http_ok=$?
  [ "$http_code" = "200" ]

  # 源 4: model live test
  curl -X POST "http://$host:18789/v1/chat/completions" \
    -H "Content-Type: application/json" \
    -d '{"model":"openclaw/default","messages":[{"role":"user","content":"ping"}],"max_tokens":64}' \
    --max-time 30 | grep -q '"content"'
  local model_ok=$?

  # 判定: 4 项里 3/4 通过 = UP
  local pass=0
  [ $port_ok -eq 0 ] && pass=$((pass+1))
  [ $proc_ok -eq 0 ] && pass=$((pass+1))
  [ $http_ok -eq 0 ] && pass=$((pass+1))
  [ $model_ok -eq 0 ] && pass=$((pass+1))

  if [ $pass -ge 3 ]; then
    echo "UP ($pass/4)"
  elif [ $pass -ge 1 ]; then
    echo "DEGRADED ($pass/4)"
  else
    echo "DOWN (0/4)"
  fi
}
```

**—— 4 源 = 端口 + 进程 + HTTP + model live test。**

**—— 判定 = 4 项里 3/4 通过 = UP。**

**—— 4 项里 1-2/4 通过 = DEGRADED。**

**—— 4 项里 0/4 通过 = DOWN。**

**—— 永远**以**端口 LISTEN 为准 (端口暴露 = 真在跑)。**

**—— 永远**不**只信 systemctl is-active (单源 = 24 小时盲区)。**

## 7/1 16:20 — VPS4 model live test fallback 失败 (probe 限制)

16:20 我**仔细**看 VPS4 的 model live test 结果，发现一个**已知**老问题——

```
$ curl -X POST vps4:18789/v1/chat/completions -d '{
  "model":"newapi-anthropic/DIY-VPS4",
  "messages":[{"role":"user","content":"ping"}],
  "max_tokens":16
}'

{"choices":[{"finish_reason":"length","message":{"content":"pong"}}]}  ← ⚠️ length 截断
```

**—— `finish_reason: length` = max_tokens=16 触发了**输出**长度限制。**

**—— 16 tokens 不够返回完整 "pong 👋" = 截断 = probe 误以为失败。**

**—— 真值 = DIY-VPS4 跑得 OK = 12 天稳态。**

**—— probe 限制 = max_tokens=16 太低 = 应该改 max_tokens=64。**

**—— 真值 ≠ probe 看到的值 = 第 32 类的**副产物** = "probe **自己**盲**了"。**

我又看 VPS4 的 fallback chain：

```
$ curl -X POST vps4:18789/v1/chat/completions -d '{
  "model":"newapi-anthropic-fallback/MiniMax-M2.7-fallback",
  ...
}'

{"error":{"code":400,"message":"invalid params: unknown model 'MiniMax-M2.7-fallback'"}}
```

**—— ⚠️ fallback model **拼错了**。**

**—— **真**配置 = MiniMax-M2-7-fallback (横线)**。**

**—— **错**配置 = MiniMax-M2.7-fallback (点)**。**

**—— **错** = new-api upstream **不认**这个 model id = 400 unknown model = fallback chain 断了。**

**—— fallback chain 断 = 如果 DIY-VPS4 挂了 = 0 fallback = 0 备份。**

**—— 0 备份 = 第 32 类的**副产物** = "我**自己**盲**了配置**"。**
